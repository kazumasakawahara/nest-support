## 用語（一行ずつ）

- **Claude Desktop**：Anthropic の Claude を Mac の画面で使うアプリ。文書の添付と音声の入力ができる
- **MCP**：Claude が手元の道具（DB の照会など）を呼ぶための決まり。道具を出す側のプログラムを「MCP サーバー」と言う
- **ゲート**：tsunagu-net の `tsunagu/gate/`。書き込みを機械で点検し、通れば DB に書く。AI は使わない。この提案では「書き込み受付」と同じ意味
- **照会口**：DB を読むだけの MCP。tsunagu-net には今、資源 DB の照会口（`tsunagu/mcp_resource.py`）しか無い
- **未確定（Pending）**：AI が作ったものが入る最初の状態。承認で確定（Active）、却下で無効（Inactive）
- **共有の根拠（SharingBasis）**：機関の間で情報を受け渡してよい法令の根拠（照合した条の号）か本人の同意。読み込みの道具だけが書く。今は 21 件
- **配布先**：ADR-008 で決めた、資源 DB と空のケース DB の雛形を配る団体（行政機関・社協など、ケース会議の中核）

## 背景

- nest-support は ADR-002 の草案で、入口を Claude Desktop に一つにし、残すアプリを「書き込み受付（ゲートの MCP）」と「読み取り専用の照会口」の二つにする方向を出した。承認も MCP に置き、案の種類に「失効」「交代」「修正」「食い違い」を足す
- tsunagu-net でも、使う人が特定の専門職（弁護士・社会福祉士）で、入力の実態が「他の機関から受けた情報提供の書面と、自分のケース記録を Claude に添付する」であることは同じ。構造化は Claude、承認は人、出力は PDF という分け方もそのまま当てはまる
- ただし tsunagu-net は、ADR-008 で「AI に送るかは配布先が決める。既定は送らない」（D7）、「MCP は読み取り専用」（D5。ADR-001 D3・D4 を変えない）と決めている。ケース DB には自由な Cypher を受ける照会口を置かない（ADR-001 D4）。承認は自分が登録したものにはできない（台帳 G-35）。この三点で nest-support と出発点が違う
- 二つの DB は「四つの約束」（共通の約束 v1.1）だけをそろえ、それ以外はそれぞれが決める（ADR-008 D9）。この提案は四つの約束を変えない

## 提案する決定

**D1 Claude Desktop を、特定の専門職が使う入口として足す。残すアプリは「書き込み受付」と「照会口」だけにする**

- 弁護士・社会福祉士が、自分の受けた情報提供の書面とケース記録を Claude Desktop に添付し、Claude が書き込みの案（未確定）を作り、書き込み受付がゲートで点検して未確定で入れ、同じ会話の中で人が一件ずつ承認する。出力は Claude が作り、PDF にする
- 残すアプリは次の二つ。どちらも使う人の Mac の中だけで動く（127.0.0.1）
  1. **書き込み受付**（新しく作る MCP）：今の入口の点検（`tsunagu/gate/intake.py`。BRS-43）を通してからゲートに渡し、未確定で書く。承認・却下もここ（D2）
  2. **照会口**：資源 DB は今の `tsunagu/mcp_resource.py` のまま。ケース DB は**決まった問い合わせの型だけ**を持つ新しい照会口にする（自由な Cypher は今後も開けない。ADR-001 D4）。型は今の読み取りの道具（`tsunagu/case/` の read・connections・candidates・assessment・members）をそのまま MCP の道具にする。見る前に閲覧を記録し（BRS-34）、支援の対象でない構成員の名前は出さない（BRS-35）。記録の本文（`Record.text`）は返さず、引用（`quote`）だけを返す
- **作らないもの**：職員向けの画面、職員ごとのトークン、職員向けの手順書、AI を使わない配布先向けの画面（河原さんの言う「道 C」）。tsunagu-net には今、画面は無いので「やめる」より「作らない」と決めることになる。ADR-008 の未決 3（配布先の職員の認証）は、D2 の「身元を MCP の設定で結ぶ」で答える
- **ADR-008 との関係**：この ADR は ADR-008 の配布の形を取り消さない。AI に送ると決めた配布先（`config/ai-sending.json` の EXT-13 が `send: true`）と、河原さんのように専門職が自分で使う場合に、Claude Desktop を入口として使う形を決める。送らないと決めた配布先は、今までどおり端末の道具（`scripts/`）で使う（未決論点 1）
- 管理者の操作（職員の登録と無効化、保存の判断、消す道具、共有の根拠の読み込み、訂正）は MCP に置かず、今までどおり管理者が端末で打つ

採用理由：使う人の入力の実態（添付・音声）に合う。tsunagu-net は画面をまだ作っていないので、今決めれば作らずに済む。nest-support と入口の形をそろえれば、管理者の手順書と引継ぎの章を似た形で書ける。

却下した案：

- **職員向けの画面を作る**：配る相手が決まっていない。入力の実態に合わない。画面と Claude の二つの入口を持つと、点検と手順書を二重に保つ
- **ケース DB にも資源 DB と同じ自由な Cypher の照会口を置く**：閲覧の記録（BRS-34）と、支援の対象でない構成員の名前を伏せる決まり（BRS-35）を素通りできる。ADR-001 D4 の理由がそのまま残っている
- **ADR-008 の配布の形をやめ、専門職の手元だけにする**：配布先の中核の団体で使う形（ADR-008 D1）は河原さんが決めたもので、この提案の範囲を超える

**D2 承認を MCP に置く（ADR-008 D5「MCP は読み取り専用」の改め）。承認は人の身元（Staff）に結ぶ**

- 改める箇所：ADR-008 D5 の「Claude は直接書かない（MCP は読み取り専用。ADR-001 D3・D4 は変えない）」。**書き込み受付の MCP は、ゲートを通す書き込み（未確定で入れるだけ）と、承認・却下を行う。** 変えないこと：Claude が Cypher で直接書く道は作らない。DB に書くのはゲートだけ。AI 由来は必ず未確定で入る（BRS-03）
- **身元の結び方**：書き込み受付は、使う人の Mac で、その人の Staff ID を設定ファイルから読んで起動する。道具の引数に Staff ID を取らない（Claude が別の人の名で承認する余地を作らない）。照会口も同じ設定から Staff ID を読み、閲覧の記録（BRS-34）をその人に結ぶ
- **歯止め**（nest-support ADR-002 D2 と同じ）
  1. 承認・却下の道具は、Claude Desktop の設定で「毎回、人に可否を聞く」にする
  2. 承認の道具は、直前に同じ対象の引用を出した印（一時の印。有効は数分）を受け取らないと動かない
- **tsunagu-net に残る点検は、MCP の承認でもすべて効かせる**：Approver でない人は承認できない、自分が登録したものは承認できない（G-35。未決論点 2）、【未照合】の根拠による共有の記録（Disclosure）は承認できない（BRS-02）
- **まとめての承認の扱い**：tsunagu-net には `approve_many`（200 件まで。T-20a）がある。MCP には一件ずつの道具だけを出し、まとめての承認は端末の道具に残す（nest-support は作らないと決めている。tsunagu-net は情報提供の書面一通から記録が多く出るので、まとめてをやめるかは未決論点 5）

却下した案：

- **承認は端末の道具のまま（今の形）**：案を見た会話と承認が離れる。使う人が端末を打てることを前提にできない
- **Staff ID を道具の引数で受け取る**：Claude が任意の職員の名で承認できる
- **承認を Claude に任せる**：BRS-03・BRS-09（判定しない）に反する

**D3 書き込みの案に「失効」「交代」「修正」「食い違い」を加える。新規以外も必ず未確定を通す**

tsunagu-net の正典の項目に当てると、次のようになる（nest-support の禁忌・キーパーソンにあたるものは tsunagu-net に無い）。

| 種類 | tsunagu-net での例 | 承認で DB に起きること（今の正典の項目） | 今の扱い |
|---|---|---|---|
| 新規 | 書面から記録・人・関わりを作る | 今のまま（BRS-43・44） | 入口の点検とゲートがある |
| 失効 | 機関の関わりが終わった、世帯から転出した | `Involvement.endDate`・`howEnded`、`MEMBER_OF.until` に値が入る | `update.py` が人の操作として直接書く（空の項目を埋める・`howEnded` を Ongoing から変える） |
| 交代 | 担当のケアマネジャー・相談支援専門員・後見の担当者が代わった | 前の `ASSIGNED_TO` に `until`、新しい `ASSIGNED_TO` を `since` つきで作る。機関そのものが代わったときは、前の関わりを終え（失効）、新しい関わりを作る（新規） | 人の操作として直接書く |
| 修正 | 生年月日の打ち間違い、関わりの種類の取り違え | `Correction`（前の値・新しい値・理由）と `CORRECTS`。記録（Record）は直さず、新しい記録を作る（BRS-25） | Administrator が理由を付けて直接訂正する（`correct.py`） |
| 食い違い | 前の書面と、新しい書面の内容が合わない | 新しい `Record`（未確定）から既にある `Record` へ `CONTRADICTS {claim, raisedAt}`。裁定は Administrator（BRS-06・G-41） | ゲートは張れる |

- **今は人の操作として直接書いているもの（失効・交代・修正）を、AI が案を出すときは未確定を通す**。人が自分で端末から直すとき（今の `update.py`・`correct.py`）は今のまま残す
- 未確定を通す形は、nest-support ADR-002 D3 の**変更の案のノード**（`ChangeProposal`。接頭辞 `CHP`、列挙 `changeKind`：`Expire`・`Handover`・`Correct`・`Resolve`、関係 `TARGETS`・`EVIDENCED_BY`）を**同じ名前で**足すことを提案する。二つの DB で同じ名前・同じ意味にすれば、Claude のスキルと管理者の手順書を共通の言葉で書ける
- 承認したとき、ゲートは同じトランザクションの中で、今の `update.py`（失効・交代）か `correct.py`（修正）の点検をそのまま通して当てる。点検で止まる変更は、案の段でも止める（例：記録の本文・確度は修正の案でも直せない）
- **根拠を必ず付ける**：変更の案には、根拠の記録（`EVIDENCED_BY` → `Record`）を求める。他の機関の書面が根拠なら、その記録は提供元（`PROVIDED_BY`）と二段の確度（BRS-44）を持つ

却下した案：

- **失効・交代・修正は人の操作だから未確定を通さない**：Claude が案を出す以上、人が内容を見て決める段が要る。関わりを「終わった」とする案が点検なしに通ると、関わるべき機関の候補（ADR-004 D5）から機関が外れ、つながりの表から担当が消える
- **変更の案を DB の外（ファイル）に置く**：未確定の一覧に出ず、監査ログと結べない
- **tsunagu-net だけ別の名前で足す**：Claude が二つの DB を行き来するとき、同じ操作に二つの名前ができる

**D4 承認の道具の形をそろえる。却下の理由を AuditLog に残す**

- 道具（案。nest-support ADR-002 D4 と同じ名前）：`list_pending`（未確定の一覧。古い順。人は ID と続柄だけ）、`show_pending`（一件の引用と、提供元・共有の根拠。承認に要る一時の印を返す）、`approve`（一件）、`reject`（一件。**却下の理由を一行、必須**）。食い違いの裁定（`resolve_contradiction`）は、tsunagu-net では Administrator の操作なので MCP に置くかは未決論点 3
- **却下の理由**：AuditLog に `reason`（文字列。`action` が `Reject` のときだけ。一行。名前を書かない）を足す。nest-support の台帳 G-91 の提案と同じ名前。tsunagu-net の正典では、理由の文の項目は `reason`（`POSSIBLY_SAME_AS.reason`・`RetentionDecision.reason`・`Correction.reason`）と呼んでいるので、名前もそろう
- AuditLog の形を二つの DB で同じに保つため、同じ名前・同じ決まりで足すことを提案する

**D5 対象は特定の専門職。属人化してよいのは入口だけで、データと引継ぎは属人化させない**

- nest-support ADR-002 D5 と同じ。属人化してよいもの：Claude Desktop の設定、Anthropic との契約、MCP の設定ファイル（Staff ID・DB の接続先）。属人化させないもの：ケース DB と書き出しの置き場所、正典、`docs/external-api.md` と `config/ai-sending.json`、監査ログ、共有の根拠の照合の記録
- 引継ぎの章（管理者の手順書）に、nest-support と同じ 6 項目を書く。tsunagu-net では、これに (7) 共有の根拠の版（照合した日と法令の改正の状況）を次の人に渡すこと、を足す

**D6 契約の形は未決のまま。既定は変えない**

- 実データを Claude に渡せるかは、契約の形（個人向けか事業者向けか）と、配布先の判断（ADR-008 D7）で決まる。この ADR では決めない
- 決まるまで、書き込み受付とケース DB の照会口は、架空の DB と宣言した DB（`scripts/declare_fictional_db.py`）か、`config/ai-sending.json` の該当の行が埋まったときだけ動く。今の EXT-13 の止め方と同じ
- `docs/external-api.md` には、使う前に行を足す：ケース DB の照会口の結果を Claude が読むこと（今の EXT-11・12 より広い）と、書き込み受付の結果（点検の結果・未確定の ID・引用）が Claude に返ること

## nest-support との違い（一節）

tsunagu-net は、弁護士・社会福祉士が、**他の機関から受けた情報**を世帯ごとにまとめてケース会議に持ち込むための DB である。nest-support が「本人一人と家族の語り」を持つのと違い、tsunagu-net の記録の多くは他の機関の書面から来る。そのため、どの機関から、どの根拠で受けたか（共有の根拠）が、ケース会議で情報を出してよいかの前提になる。違いは次の五つ。

1. **共有の根拠を案に必ず付ける**：Claude が情報提供の書面から記録の案を作るときは、提供元（`PROVIDED_BY`）と、受けた根拠（`Disclosure` の `UNDER` → `SharingBasis`）を案に含める。根拠は読み込み済みの 21 件から選ぶだけで、Claude は根拠を作れない（`SharingBasis` は読み込みの道具だけが書く）。【未照合】の根拠による共有の記録は、MCP の承認でも確定しない（BRS-02）。根拠が分からない書面は、根拠を空にせず、人に聞く問いとして返す
2. **共有の根拠は Claude に送る根拠にならない**：共有の根拠は機関の間で受け渡す根拠であって、受けた情報を外部の事業者（Anthropic）に送ってよいかの根拠ではない。送ってよいかは、配布先・使う人の判断と契約で別に決める（ADR-008 D7、`docs/distribution/ai-sending.md`、nest-support の K-2 の文書）。この区別を、管理者の手順書と Claude のスキルの冒頭に書く
3. **会議の記録は根拠と一緒に出す**：会議（`Meeting`）は法定の会議体の根拠（`HELD_UNDER`）を持つ。Claude が会議の資料を PDF にするときは、会議の種類と根拠の表示（照合済みか【未照合】か）を必ず添え、支援の対象でない構成員の名前を出さない（BRS-35）
4. **自己承認**：nest-support は一人で使う前提で、自己承認を許して印を付ける（nest-support ADR-001 D9）。tsunagu-net は、AI の抽出を取り込んだ人がそのまま確定させないため、自己承認を禁じている（G-35）。弁護士と社会福祉士が組んで使うなら、互いに承認する形が取れる。一人で使う間をどうするかは未決論点 2
5. **ケース DB の照会口は決まった型だけ**：nest-support の照会口は Cypher を受け、伏せ字と上限で守る。tsunagu-net のケース DB は、閲覧の記録（BRS-34）を見る前に必ず書くため、決まった問い合わせの型だけを出す。Claude が自由に問い合わせを組み立てることはできない

## 撤退線

- **W1**：Claude Desktop の「毎回、人に可否を聞く」が保てないと分かったら、承認の道具を MCP から外し、端末の道具に戻す。書き込み受付（未確定で入れるだけ）は残す
- **W2**：決まった型だけの照会口では、ケース会議の準備に要る問いに答えられない（型が増え続ける）と分かったら、型の作り方を見直す。自由な Cypher は開けない（ADR-001 D4 の撤退線と同じ）
- **W3**：自己承認を禁じたままでは承認が滞る（G-35。ADR-008 W3）と試行で分かったら、承認の単位と自己承認の扱いを見直す
- **W4**：変更の案（`ChangeProposal`）の形が tsunagu-net の失効・交代・修正に合わない（例：関わりの終わりと担当の交代が一つの書面で混ざる）と分かったら、案の形を「新しい記録＋人の操作」に寄せ直す。未確定を通すことは変えない

- 四つの約束は変えない。`ChangeProposal`・`changeKind`・AuditLog の `reason` の名前を二つの DB でそろえることを、約束に足すか（v1.2）は未決論点 6

## 未決論点（河原さんに決めていただくこと）

1. **ADR-008 との関係**：この ADR を「AI に送ると決めた配布先と、専門職が自分で使う場合の入口」として足すか（提案）、tsunagu-net の対象そのものを弁護士・社会福祉士に絞り、配布先の中核の団体に配る形（ADR-008 D1）を見直すか
2. **自己承認**：tsunagu-net は自己承認を禁じている（G-35）。(a) 禁止を保ち、弁護士と社会福祉士が互いに承認する（一人で試す間は、架空の DB に架空の二人目の Approver を置く）、(b) nest-support と同じく許して印を付ける。提案は (a)。他の機関から受けた情報を確定させるので、別の人の目を通す理由が nest-support より強い
3. **Administrator の操作を MCP に置くか**：修正（訂正）と食い違いの裁定は、今は Administrator の操作。変更の案の承認で当てるとき、承認できるのを Approver にするか Administrator に限るか。nest-support ADR-002 は管理者の操作を MCP に置かないとしている
4. **関係の名前 `TARGETS` の重なり**：tsunagu-net は既に `TARGETS`（Intervention → Person/Household）を持つ。変更の案の関係に同じ名前を使うと意味が二つになる。別の名前にするなら、nest-support の側も同じ名前に直すよう知らせる
5. **まとめての承認**：tsunagu-net の `approve_many` を MCP に出さず端末だけに残すか、やめるか
6. **名前をそろえる約束**：`ChangeProposal`・`changeKind`・AuditLog の `reason` を共通の約束に足すか（v1.2）、それぞれの正典に同じ名前で書くだけにするか
7. **渡し方**：この提案を tsunagu-net にどう渡すか（tsunagu-net のセッションで ADR-009 として起こす、など）。G-40 と同じく、まだ決めていない

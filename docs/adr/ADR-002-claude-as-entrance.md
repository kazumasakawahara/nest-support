## 用語（一行ずつ）

- **Claude Desktop**：Anthropic の Claude を Mac の画面で使うアプリ。文書の添付と音声の入力ができる。この ADR では「入口」と呼ぶ
- **MCP**：Claude が手元の道具（DB の照会など）を呼ぶための決まり。道具を出す側のプログラムを「MCP サーバー」と言う。Claude Desktop は、道具を呼ぶたびに人に可否を聞く設定にできる
- **ゲート**：`nest/gate/`。書き込みの案を機械で点検し、通れば DB に書く。AI は使わない。この ADR では「書き込み受付」と同じ意味で使う
- **照会口**：`nest/mcp_personal.py`・`nest/mcp_resource.py`。DB を読むだけの MCP。実名・かな・電話・住所・生年月日を返さない（コードの中では「読み取りの包み」と呼んでいる。同じもの）
- **未確定（Pending）**：AI が作ったものが入る最初の状態。人が承認すると確定（Active）、差し戻すと無効（Inactive）になる
- **仮名（displayCode）**：本人を指す `C-` ＋ 6 字の記号。実名との対応は手元の道具だけが持つ
- **Staff**：この DB を使う人の記録。承認・記録の書き手を指す ID（`STF-…`）

## 背景

- ADR-001 は「Claude は案を作るだけ、ゲートが点検して未確定で入れ、人が承認して確定する」（D6）と決め、MCP は読み取りだけにした。承認は手元のコマンド（`scripts/review_proposals.py`。N-44）で、記録の入力は職員向けの画面（field-ui）で、職員の身元は職員ごとのトークン（`scripts/staff_token.py`。N-37）で行う形になっている
- 段階 I まで作って見えたこと
  - 使う人は、相談支援専門員・弁護士・社会福祉士のうちの特定の一人か二人で、最初は河原さん自身。画面と手順書を一式そろえて配る相手がいない
  - 入力の実態は「語り・面談記録・書面を Claude に添付する」「音声で話す」であり、画面に項目を打つ形ではない。構造化（案を作る）は Claude の仕事で、人の仕事は「案を見て承認する」こと
  - 承認を手元のコマンドで打つと、Claude の会話（案を作った場所）と承認（端末）が離れる。引用を見てから決める（D9）流れが、画面を行き来する手間で崩れやすい
  - 今の案の形は「新しく作る」だけで、現場で多い「禁忌がもう当てはまらない（失効）」「キーパーソンが代わった（交代）」「書き間違いを直す（修正）」「前に聞いた話と食い違う（食い違い）」を、案として出す道が無い。これらを人が Cypher で直接書くと、ADR-001 D6 の「書くのはゲートだけ」が守れない
  - 画面（field-ui・SOS）は、Claude に送らない経路として歯止めを分けた（G-85）。入口を Claude に一つにすると、この分け方が要らなくなる
- 外に送るものの約束は変わらない。実データを Claude に渡せるかは契約の形（個人向けか事業者向けか）で決まり、まだ決めていない（G-80）。この ADR はその答えを先取りしない

## 決定

**D1 入口は Claude Desktop。残すアプリは「書き込み受付（ゲート MCP）」と「読み取り専用の照会口」の二つだけ**

- 使う人は Claude Desktop だけを開く。語り・面談記録・書面は添付し、話したいことは音声で入れる。構造化は Claude が「未確定の案」として出し、受付（MCP）がゲートで点検して未確定（Pending）で DB に入れる。承認は同じ会話の中で人が一件ずつ行う（D2・D4）。出力は Claude が作り、PDF にする（`html-to-pdf`）
- 残すアプリは次の二つ。どちらも MCP サーバーで、使う人の Mac の中だけで動く（127.0.0.1）
  1. **書き込み受付**（新しく作る MCP。`nest/gate/` を呼ぶ）：案を受け取り、点検し、未確定で書く。承認・差し戻しもここ（D2）
  2. **照会口**（今の `nest-personal`・`nest-resource`）：読むだけ。伏せ字と上限は今のまま
- **やめるもの**
  - 職員向けの画面 **field-ui**（`field-ui/`。記録の入力・録音の画面）。入力は Claude Desktop への添付と音声に替える
  - **職員ごとのトークン**（`scripts/staff_token.py`・`nest/auth.py` の職員の認証。N-37）。身元は MCP の設定で結ぶ（D2）
  - **職員向けの手順書**（`docs/OPERATIONS.md` の職員向けの段、`docs/QUICK_START.md`・`docs/SETUP_GUIDE.md` の職員向けの部分、`docs/VOICE_RECORDING_GUIDE.md`）。残す文書は **管理者の手順書**（`docs/OPERATIONS.md` を「専門職一人＋管理者」向けに書き直す。引継ぎの章を足す。D5）と、スキルの冒頭に置く**定型の頼み方**（Claude への頼み方を四つ。段階 L の案）だけ
  - **道 C**（河原さんの呼び方：AI を使わない配布先向けの画面）。この名前はリポジトリの文書には無い【要確認：どの文書の呼び方か】。nest-support では「AI を使わない人のための入口」を作らない。AI を使わない事業所に配るのは tsunagu-net の側の論点（ADR-008 D7）で、nest-support は引き受けない
- 管理者の操作（最初の管理者の作成・職員の登録と無効化・本人の登録・バックアップ・廃棄・点検）は MCP に置かず、今までどおり管理者が端末で打つ（`scripts/`）。Claude からは呼べない

却下した選択肢：

- **field-ui を作り直して残す**：配る相手がいない。入力の実態（添付・音声）に合わない。画面と Claude の二つの入口を持つと、歯止め（G-85 の呼び出し元の分け方）と手順書を二重に保つことになる
- **承認だけ端末のコマンドに残す（今の N-44 のまま）**：案を見た会話と承認が離れる。一件ずつ引用を見てから決める（D9）流れが崩れやすい。使う人が端末を打てることを前提にできない
- **Claude Code（端末）を入口にする**：ファイルの操作と DB の起動まで Claude に任せられるが、音声と添付の入口として専門職に向かない。管理者の作業の道具としては残す（管理者の手順書に書く）

**D2 承認を MCP に置く（ADR-001 D6「MCP は読み取りだけ」の改め）。承認は人の身元（Staff）に結ぶ**

- 改める箇所：ADR-001 D6 の「Claude は直接書かない。MCP は読み取りだけにする」。**書き込み受付の MCP は、ゲートを通す書き込み（未確定で入れる）と、承認・差し戻しを行う。** 変えないこと：Claude が Cypher で直接書く道は作らない。DB に書くのはゲートだけ。AI 由来は必ず未確定で入る。承認は書き込みと別の操作で、一件ずつ（D9）
- **身元の結び方**：書き込み受付の MCP は、一人の専門職の Mac で、その人の Staff ID を設定ファイル（`~/.config/nest/` の下。中身は Claude に読ませない）から読んで起動する。道具の引数に Staff ID を取らない。Claude が別の人の名で承認する余地を作らない。承認は `(Staff)-[:APPROVED {at, selfApproval}]->(対象)` と AuditLog に残る（正典 §7。変えない）
- **二つの歯止め**（コードで強制する）
  1. 承認・差し戻しの道具は、Claude Desktop の設定で「毎回、人に可否を聞く」にする（「この会話では常に許可」にしない）。管理者の手順書に書き、doctor では点検できないので「人が確かめる」とする
  2. 承認の道具は、直前に同じ対象の引用を出した印（`show` が返す一時の印。有効は数分）を受け取らないと動かない。引用を見ずに承認する操作を機械で止める（D9 の「引用を並べて見せてから行う」を道具の形にする）
- 管理者だけの操作（職員の登録・無効化、保存の判断、廃棄）は MCP に置かない（D1）
- 読み取りの照会口は変えない。書き込み受付と照会口は別のプロセスにし、照会口に書く道具を足さない（読むだけの道具が「読むだけ」であることを試験で固定し続ける）

却下した選択肢：

- **Claude が自分で Cypher を書いて MCP で実行する**：ADR-001 D6・D7 を捨てることになる。点検（引用が原文にあるか、確度の格上げが無いか）が無くなる
- **承認を Claude に任せる（Claude が引用と案を照らして自動で承認）**：約束 4-5（AI 由来は未確定）と D9（人が一件ずつ）に反する。出力は提案であって判断ではない
- **Staff ID を道具の引数で受け取る**：Claude が任意の職員の名で承認できる。身元の結びつきが保てない

**D3 書き込み受付の案に、新規のほかに「失効」「交代」「修正」「食い違い」を加える。新規以外も必ず未確定（Pending）を通す**

案の種類は五つ。どれも Claude が JSON で出し、ゲートが点検し、未確定で入り、人が一件ずつ承認して初めて DB の事実が変わる。

| 種類 | 何をするか | 承認で DB に起きること（正典の項目） |
|---|---|---|
| 新規 | 事実・記録・人・関わりを新しく作る（今の案の形。N-11〜N-24a） | ノード・関係が `Active` になる（今のまま） |
| 失効 | 禁忌・推奨ケアが当てはまらなくなった日を書く | `NgAction.validTo`・`CarePreference.validTo` に日付が入る。ノードは消さない・`Inactive` にしない（その日まで有効だった事実として残る） |
| 交代 | キーパーソンなど、本人の周りの人の役割が代わった | 前の `RELATED_TO {kind: KeyPerson}` に `until` と `status: Inactive`、新しい `RELATED_TO` を `since` つきで作る（正典 §4.3「交代・終わりは張り替えない」。依頼文の endDate／startDate は、正典では `RELATED_TO` の `until`／`since`。関わり（`Involvement`）なら `endDate`／`startDate`） |
| 修正 | 書き間違い・読み間違いを直す | 直した内容を新しいノードとして作り、元のノードを `Inactive` にする（AuditLog `Inactivate`）。元のノードは消さない。二つは同じ `requestId` で結ぶ |
| 食い違い | 新しく聞いた話が、既にある事実と合わない | 新しい `Record`（未確定）から既にある事実へ `CONTRADICTS {claim, raisedAt}`。事実のほうは変えない（ADR-001 D5。ゲートは今も作れる：`write.py`）。裁定（`resolvedAt`・`resolution`・`resolvedBy`）は人が承認の道具で行う（AuditLog `ResolveContradiction`） |

- **「新規以外も Pending を通す」の形**：失効・交代（前の関係の終わり）・修正・裁定は、既にある `Active` のものを変える操作で、変える前の値と後の値を両方残す場所が今の正典に無い。そこで、**変更の案を一つのノードとして持つ**ことを正典に提案する（この ADR の承認と、正典の版上げの手順を経てから足す。承認前は足さない）
  - ラベル `ChangeProposal`（接頭辞 `CHP`）。項目：`changeProposalId`✅、`kind`✅（列挙 `changeKind`：`Expire`・`Handover`・`Correct`・`Resolve`）、`targetLabel`✅、`targetId`✅、`payload`✅（変える項目と値。文字列の JSON。名前・住所など伏せる項目を入れない）、`status`✅（`Pending`→`Active`＝適用した／`Inactive`＝差し戻した）、`origin`✅、`registeredAt`✅
  - 関係：`(ChangeProposal)-[:EVIDENCED_BY]->(Record)`（根拠。失効・交代・修正にも引用を求める。根拠が無い案はゲートが止める）、`(ChangeProposal)-[:TARGETS]->(対象)`
  - 承認の操作で、ゲートが同じトランザクションの中で対象に `payload` を当て、`ChangeProposal` を `Active` にし、AuditLog（`Approve` と、対象への `Inactivate`／`ResolveContradiction`）を残す。差し戻しは `Inactive` にして何も当てない
  - 列挙 `auditAction` に `Expire`（失効を書いた）を足すかは未決論点 4
- 人が直接知ったこと（職員の観察）を根拠にするときは、先に職員の `Record`（`kind: Observation`）を作る（台帳 G-63 の決まりのまま）
- 新規の案の形（`nest/gate/intake.py` の JSON）は変えない。失効・交代・修正・食い違いは `changes` の欄として同じ依頼に足すか、別の道具にするかは実装の段階で決める（点検の決まりは同じ）

却下した選択肢：

- **人が Cypher で直接直す（今の状態）**：ADR-001 D6 に反する。監査ログが残らない。何を根拠に直したかが残らない
- **変更を未確定を経ずに `Active` へ直接書く（人の操作だから）**：Claude が案を出す以上、人が内容を見て決める段が要る。新規だけ未確定を通し、失効・修正は通さないと、禁忌を「失効」させる案が点検なしに通る
- **変更の案を DB の外（ファイル）に置いて、承認のときだけ DB に書く**：二つの置き場所ができ、未確定の一覧（`list`）に出ない。監査ログと結べない
- **元のノードを上書きして「修正」する**：確度や引用との結びつきが崩れる。前の正典 §7.10 と正典 §4.3 の「張り替えない」に反する

**D4 承認の操作は `scripts/review_proposals.py`（N-44。台帳 G-89）の振る舞いをそのまま MCP の道具にする**

- 道具（案）：`list_pending`（未確定の一覧。古い順。本人は仮名だけ）、`show_pending`（一件の根拠の引用。承認に要る一時の印を返す）、`approve`（一件。`selfApproval` を自動で付ける）、`reject`（一件。**差し戻しの理由を一行、必須**）、`resolve_contradiction`（食い違いの裁定）
- **一件ずつ**。まとめての承認の道具は作らない（`approve_many` は使わない。G-89 (a)）。AI 由来を一括で承認しない（D9）
- **自己承認の印**：自分で登録したものを承認したら `selfApproval: true`（`APPROVED` と AuditLog）。一人で使う間はほぼ全部が自己承認になる。これは隠さず、月に一度、管理者の手順書の点検で自己承認の数を見る（撤退線 W2 のため）
- **差し戻しの理由**：台帳 G-91 の提案を採用し、AuditLog に `reason`（文字列。`action` が `Reject` のときだけ。一行。名前を書かない）を足す。MCP の `reject` は理由が無いと動かない（コマンド版では任意だったが、Claude との会話では理由を聞いてから呼べるので必須にする）。AuditLog の形は tsunagu-net と同じに保つため、K-3 の提案文に同じ名前で入れる
- 承認・差し戻しの結果は、引用と一緒に Claude が人に読み上げる形で返す（`shown` と同じ）。実名・連絡先は返さない（照会口と同じ伏せ字）
- 端末のコマンド `scripts/review_proposals.py` は、MCP ができた後も管理者の予備の道具として残す（Claude Desktop が使えないときの承認）。どちらも同じ `nest.gate.approve` を呼ぶ

却下した選択肢：

- **差し戻しの理由を任意のまま**：後で同じ案がまた来たときに見分けられない（G-91 の理由）。会話なら理由を聞く手間が無い
- **自己承認を禁じる（tsunagu-net G-35 と同じにする）**：一人で使う前提では承認が止まる。ADR-001 D9 の判断を変えない

**D5 対象は特定の専門職。まず河原さんが使い、次の一人に渡す。属人化してよいのは入口だけで、データと引継ぎは属人化させない**

- **属人化してよいもの（入口）**：Claude Desktop の設定、Anthropic との契約、MCP の設定ファイル（Staff ID・DB の接続先）、スキルの好み。これらは使う人ごとに作り直す
- **属人化させないもの（データと引継ぎ）**
  - DB（Docker のボリュームと `docker compose` の定義）、バックアップの置き場所と周期、正典（`docs/SCHEMA.md`・`docs/SEMANTICS.md`）、外に送るものの一覧（`docs/external-api.md`）と契約の確認の記録、監査ログ
  - 本人の仮名と実名の対応は、使う人の手元ではなく、管理者が決めた置き場所に置く（場所と権限は管理者の手順書に書く）
- **引継ぎの章**（管理者の手順書に足す。段階 M の案）に書くこと：(1) 次の人を `Staff` として登録し（`new_staff`）、前の人を `Inactive` にする（前の人の承認の記録は残る） (2) 次の人の Mac に MCP の設定を作る（雛形と、埋める項目） (3) DB とバックアップの所在と、戻せることの確かめ (4) 契約の確認の記録を次の人の契約で作り直す（記録が無い間は、照会口と受付は実データで動かない。NEXT-01・02 のまま） (5) 前の人の Claude Desktop の会話の履歴の扱い（Anthropic 側の保存期間と削除。K-2 の文書に沿う） (6) 引継ぎを AuditLog で確かめられること（前の人の最後の操作と、次の人の最初の操作）
- 二人目以降に渡すときの前提：この ADR の受け入れ試験（下）を次の人の Mac で架空の事例で一通り流せること

却下した選択肢：

- **複数の職員が同時に使う前提で作る**：対象が特定の一人か二人で、同時の編集・権限の分け方（tsunagu-net の `Approver`）を持ち込むと、ADR-001 D9（自己承認・役割は 2 値）を変えることになる。複数の事業所で一つの DB を使う話が出たときに別の ADR で決める

**D6 契約の形（個人向け／事業者向け）は未決のまま。歯止めは変えない**

- 実データを Claude に渡す経路の契約（個人向けプランか、事業者向けの契約か。台帳 G-80）は、この ADR では決めない（未決論点 1）
- 決まるまで、受付と照会口は今の歯止めのまま動く：契約の確認の記録と機能の設定がそろうか、架空の印（`NestLiveProbe`）のある DB のときだけ（NEXT-01・02。台帳 G-54 (3)）。この ADR の実装と試験は、すべて架空の事例で行う
- 書き込み受付の MCP も、照会口と同じ歯止め（`require_personal_allowed`）を通す。受付の側に別の抜け道を作らない
- 画面（`caller="screen"`）が無くなるので、呼び出し元の分け方（G-85）は `mcp` だけになる。SOS を残すかで変わる（未決論点 3）

## 撤退線

- **W1**：Claude Desktop の設定で「毎回、人に可否を聞く」が保てない（設定が変わる・Claude Desktop の仕様が変わる）ことが分かったら、承認の道具を MCP から外し、端末のコマンド（N-44）に戻す。書き込み受付（未確定で入れるだけ）は残す
- **W2**：監査ログで、`show_pending` を経ない承認が機械で止まっているのに、承認までの時間が極端に短い（引用を読んでいない）様子が続いたら、承認の単位と見せ方を見直す（ADR-001 W2 と同じ）
- **W3**：失効・交代・修正の案が、変更の案（`ChangeProposal`）の形では現場の言い方に合わない（一つの話で三種類が混ざる）と分かったら、案の形を「新しい記録＋人の裁定」に寄せ直す。未確定を通すことは変えない
- **W4**：次の一人に渡したとき、引継ぎの章のとおりに受け入れ試験が流せなければ、渡す前に章を直す。データの所在が使う人の Mac にしか無い状態になっていたら、属人化していると見て D5 を見直す
- **W5**：契約の形が決まらず、実データを Claude に渡せない期間が長引くなら、Claude を使わない入口を nest-support で持つか（D1 で却下した道）を別の ADR で改めて検討する。この ADR の中では復活させない

## 未決論点

1. **契約の形**（台帳 G-80）：実データを Claude に渡す経路を、個人向けプランのままにするか、事業者向けの契約（API か Team／Enterprise）にするか。決まるまで実データは渡さない。K-2 の文書（説明と同意）が「確かめること」を一覧にする
2. **変更の案の正典への足し方**（D3）：`ChangeProposal` を一つのラベルにするか、種類ごと（失効・交代・修正）に分けるか。tsunagu-net に同じ名前で提案するか（K-3）。承認前は足さない
3. **SOS（`sos/`）**：河原さんの依頼文はやめるものに SOS を挙げていない。SOS は駆けつける人向けの画面で、Claude を使わない。残すなら、呼び出し元 `screen` の歯止め（G-85）と共通トークン（`APP_ACCESS_TOKEN`）が残る。やめるなら、緊急時の確認は Claude Desktop の `emergency-protocol` と「手元の緊急連絡カード」に寄せる。**どちらかを河原さんが決める**
4. **`auditAction` に `Expire` を足すか**：失効の承認を `Approve`（変更の案）だけで残すか、対象への操作としても残すか
5. **音声と文字起こし**：録音の受け取り（`nest/voice.py`）と Gemini の文字起こし（NEXT-03）は、音声を Claude Desktop が直接受けるなら要らない。残す理由（文字起こしの原文を DB に残したい、など）があるか
6. **道 C の出所**：「道 C」の呼び方がどの文書に由来するか。リポジトリには無い【要確認】
7. **`show_pending` の印の有効時間**と、同じ会話で複数の件を続けて見るときの扱い（印は一件ごとか）
8. **Claude Desktop の「毎回聞く」設定を人が確かめる方法**：doctor では見えない。管理者の手順書に手順を書くだけでよいか
9. **仮名と実名の対応の置き場所**（D5）：使う人の手元か、管理者が決めた場所か。今の文書（external-api 注 1）は「使う人の手元」と書いている
